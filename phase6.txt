2. Format-2 production layout

<batch>/BACKUP-INFO.txt
<batch>/VMs/utm__ArchLinux-02-27-utm-6a667c24/ArchLinux 02.27.utm/...

Each direct child of VMs/ is one VM's container, and its sources are copied inside it under their own names. Identity comes only from the manifest entry whose Directory names the container.
Container naming: <providerId>__<local id>. Any character outside [A-Za-z0-9_-] becomes -. The local-id part is truncated at 64characters. If the name was changed, or collides itively, a - and an 8-hex SHA-256 of the canonical id are appended. Names are assigned in canonical-id order.

Deviation from your example: dots are also replaced, so the example becomes utm__ArchLinux-02-27-utm-…, not utm__ArchLinux-02.27. I did this so no name can ever be .. or contain a separator. Say if you want dots kept.
                                                                                                                               3. Manifest and write ordering

1. The guard checks compatibility.
2. Input is validated, and the manifest is built and verified by the writer's round-trip check. Unsafe names fail here, before    any file exists.
3. .incomplete-<batch>/VMs/ is created.
4. Each VM's sources are copied into its container.                                                                            5. BACKUP-INFO.txt is written last among the cont
6. The marker is created or updated through the guard, only after the batch is complete.
7. The incomplete directory is moved to its final name.
8. Change-tracking acknowledgement, for UTM VMs only.

The manifest holds Format-Version: 2, an offset-aware Time, one VM: block per entry (Provider, VM-ID, Name, Directory), and the comment last. The comment is trimmed on the way in and out, as before.

4. Root-metadata semantics
- No marker is created when a backup starts.
- A marker is created when the first format-2 batch is complete, and before the batch is published.                            - An existing marker at format 2 from the same aphanged. Otherwise it is rewritten with created.*kept and last.written.by.version updated.
- A newer or invalid marker is refused.

Trade-off: if the publish move fails after the marker is written, the medium declares format 2 with no format-2 batch. That is consistent, and nothing is shown for the failed backup. It does mean the marker can exist after a failed backup. I chose this over the reverse order, which can leave a published format-2 batch with no marker.
